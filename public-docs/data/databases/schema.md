## Table model

At the protocol/API level, a Table looks like:

- **`id`**: string
- **`starshipId`**: string
- **`name`**: string (max 200)
- **`slug`**: string (max 100, unique per starship)
- **`description`**: string (max 2000, defaults to `""`)
- **`columns`**: `StarshipTableColumn[]`
- **`primaryKey`**: `string | null` (optional)
- **`physicalTable`**: string (the physical Postgres table name, exposed for SQL)
- **`archived`**: boolean
- **`createdAt` / `updatedAt`**: ISO8601 strings

Physical storage:

- **Registry table**: `starship_tables`
  - `columns_meta_json` (JSONB): the author column metadata
  - `primary_key` (VARCHAR, nullable)
  - `schema_name` (`db_<starshipId>`), `physical_table` (the real table name)
- **Data**: a real Postgres table at `db_<starshipId>.<physical_table>`, with your columns as typed Postgres columns plus the hidden `__id` / `__row_key` / `__created_at` / `__updated_at` columns.

## Column model (`StarshipTableColumn`)

Each column is an object with:

```json
{
  "name": "status",
  "description": "Current workflow stage",
  "type": "enum",
  "format": "text",
  "constraints": { "required": true },
  "enum": { "options": ["todo", "doing", "done"] }
}
```

### Required fields

- **`name`**: required
  - Must match `^[a-zA-Z0-9_]+$`
  - Max length: 63
  - Must be unique within `columns`
  - Must not start with `__` (reserved for the hidden bookkeeping columns)

All other fields are optional, but some become required depending on `type` (see below).

## Column types (`column.type`)

Supported types and how they map to Postgres:

| `column.type` | Postgres type | Notes |
| --- | --- | --- |
| `string` (default) | `text`, or `varchar(N)` when `maxLength` is set | |
| `number` | `double precision`, or `numeric` when `format` is `currency`/`percentage` | autoincrement PKs use `bigint` IDENTITY |
| `boolean` | `boolean` | |
| `date` | `date` | stored as ISO date-only `YYYY-MM-DD` |
| `datetime` | `timestamptz` | ISO instant; requires `Z` or an offset, canonicalized to `...Z` |
| `json` | `jsonb` | any JSON value accepted |
| `enum` | `text` + `CHECK (col IN (...))` | single-select string |
| `reference` | `text` | stores the soft key of the referenced row/card |

> Note: there is no computed/formula column type. For derived or aggregated reads, use the read-only [SQL surface](./sql.md).

## Column formats (`column.format`)

Formats are primarily display hints for UI/export, and they influence numeric storage precision:

- `text`
- `number`
- `currency` (stored as `numeric`)
- `date`
- `datetime`
- `percentage` (stored as `numeric`)

## Constraints (`column.constraints`)

Supported constraint keys:

- `required?: boolean`
- `nullable?: boolean`
- `unique?: boolean`
- `autoincrement?: boolean`
- `default?: unknown`
- `min?: number`, `max?: number`
- `minLength?: number`, `maxLength?: number` (bounds on the string **value** length, not the column name; the server validates `maxLength` in the range 0-63 and, when set, stores the column as `varchar(maxLength)`. Leave `maxLength` unset for unbounded `text` — that is the right choice for long values like URLs or emails.)
- `pattern?: string` (JS regex string; validated server-side)

Important server rules:

- **`constraints.unique` is currently only supported for the Table `primaryKey` column.**
- **`constraints.autoincrement` is only supported for a `number` column that is also the Table `primaryKey`.**

These rules are enforced by the database: enum/bounds become Postgres `CHECK` constraints, and the primary key backs the `__row_key` `UNIQUE` constraint.

## Autoincrement columns

For `constraints.autoincrement: true`, the column is created as a Postgres `bigint GENERATED BY DEFAULT AS IDENTITY` column. On write, when the field is missing the database allocates the next integer.

Notes:

- Works for `type: "number"` only.
- Must be the Table `primaryKey` column.
- Allocation is handled by Postgres IDENTITY (safe under concurrent writes).
- You may still provide an explicit value (it overrides the generated one).

Example:

```json
{
  "primaryKey": "id",
  "columns": [
    { "name": "id", "type": "number", "constraints": { "autoincrement": true, "unique": true } },
    { "name": "name", "type": "string", "constraints": { "required": true } }
  ]
}
```

Here `id` is also the `primaryKey`, which is the only reason `unique: true` (and `autoincrement`) is allowed on it; both constraints are rejected on non-primaryKey columns.

## Enum columns

For `type: "enum"`, `enum.options` is required:

```json
{
  "name": "status",
  "type": "enum",
  "enum": { "options": ["todo", "doing", "done"] }
}
```

Writes are validated (and enforced by a Postgres `CHECK`) so the stored value must be one of the configured `options`.

## Reference columns

For `type: "reference"`, `reference.target` is required. The value is stored as a **soft text key** (the referenced row's primary key value, or the task card id), not a foreign key.

### Reference to a task card

```json
{
  "name": "task",
  "type": "reference",
  "reference": { "target": { "kind": "task_card" } }
}
```

### Reference to a row in another Table

```json
{
  "name": "account",
  "type": "reference",
  "reference": {
    "target": { "kind": "table_row", "tableIdOrSlug": "accounts" },
    "labelColumn": "name"
  }
}
```

Notes:

- `tableIdOrSlug` may be a Table id or a slug.
- Reference resolution uses the **target Table's primaryKey** (it resolves by `__row_key`), so the target Table must define a `primaryKey`.
- `labelColumn` is used when hydrating human-readable labels via the [`refs:resolve` endpoint](./api.md#batch-resolve-references).

## Schema evolution (PATCH)

Updating a Table's `columns` compiles to `ALTER TABLE` statements. Supported changes:

- Add a column (with an optional `default` to backfill existing rows)
- Drop a column
- Change nullability
- Change the default value
- Update enum/bound `CHECK` constraints
- Toggle the `primaryKey` (reconciles the `__row_key` `UNIQUE` constraint)

Rejected (destructive) changes return a `400`:

- Changing a column's logical `type` (e.g. `string` to `number`)
- Toggling `autoincrement` on an existing column

To make a rejected change, create a new column (or a new Table) and migrate the data.

## `primaryKey`

`primaryKey` (when set) must match an existing column name.

What it enables:

- `POST .../rows:upsert` with `mode: "upsert"`
- The `__row_key` `UNIQUE` constraint (stable, deduplicated row identity)
- Table-row reference resolution (so other Tables can reference these rows reliably)
